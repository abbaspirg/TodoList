# Madrasa Meelad Fest Manager

A plain HTML/CSS/JS mobile app (wrapped natively via Capacitor, same "no
build step" approach as this repo's earlier Todo app) + Firebase, for
running a Madrasa Meelad Fest end-to-end: register students into
competing Groups (any number, most often 2), define categories and
competition items, register participants, let judges score live, compute
item-wise results and each Group's grand total, and auto-generate
shareable result posters with the winner's photo.

## Project Structure

```
mobile/
  www/         the actual app: index.html, style.css, js/ (views, router, data access)
  android/     native Android project, generated by `npx cap add android`
  scripts/     write-build-config.mjs — bakes one institution into a build
  package.json @capacitor/* dependencies
firestore.rules, firestore.indexes.json
.github/workflows/android-build.yml   debug APK on every push; per-institution build on demand
```

There is no server component — see *Why no Cloud Functions* below.

## Running it on a computer

The Android app is a wrapper around `mobile/www/`, so the same app runs in
any modern browser — there's no separate desktop build to maintain.

`.github/workflows/pages.yml` publishes it to **GitHub Pages** on every
push. From that URL:

- **Windows / Mac / Linux** — open it in Edge or Chrome, then
  **⋮ → Apps → Install this site as an app**. It gets a Start-menu entry,
  its own window and a taskbar icon, and behaves like an installed program.
- **Parents and students** can simply open the link to follow live results,
  with nothing to install.

Everything points at the same Firebase project, so a judge scoring on a
phone updates a leaderboard on a laptop in the same second.

Two pieces of setup, both one-off:

1. **Enable Pages**: repo Settings → Pages → Source = **GitHub Actions**.
2. **Set the project**: repo Settings → Secrets and variables → Actions →
   **Variables** → add `FIREBASE_CONFIG` (the config JSON) and optionally
   `INSTITUTION_NAME`. A *variable*, not a secret — a Firebase web config
   isn't secret, and Actions masks secrets in a way that would corrupt it.
   Without it the site still deploys and just shows its setup screen.
3. **Authorize the domain**: Firebase console → Authentication → Settings →
   Authorized domains → add `<your-user>.github.io`, or sign-in is refused.

Note the poster's Download and Share use ordinary browser APIs here rather
than the native plugins; downloading works well on desktop, while sharing
falls back to a download where the browser has no share sheet.

## Local Test Mode (no Firebase needed)

The app installs and runs fully without any setup: tap **"Try it without a
project"** on the setup screen and every screen runs against `localStorage`
on the device instead of Firestore — students, groups, categories, items,
registrations, judge scoring (including automatic ranking, grading and group
totals), results, and posters all work, they just don't sync anywhere. The
login screen becomes a role picker ("Continue as Admin" / "Continue as
Judge") instead of an email/password form. Admin → Dashboard has "Load demo
data" and "Reset local data" buttons.

This is meant for trying out the app or demoing the workflow — connect a real
Firebase project (above) before running an actual fest, since nothing local
is shared between devices.

### Demo data

Admin → Dashboard → **"Load demo data"** replaces local data with a
ready-made fest (see `mobile/www/js/demo-data.js`), so every screen has
something realistic to show without typing it in:

- 3 groups, 3 categories (Sub Junior / Junior / Senior), 15 students —
  some with photos, some without, to cover both poster layouts.
- 6 items spanning each state worth demoing: three fully scored and
  published, one scored but **awaiting publish**, one **half-scored** (only
  the first of two judges has submitted, so it's still open in the Judge
  Panel), and one **untouched** with registrations ready.
- 3 judges with overlapping item assignments; sign in as one to finish
  scoring the open item and watch results and the leaderboard update live.
- Marks chosen to span every grade band (A/B/C and below-C), including a
  group item scored out of 20 rather than 10.

Scores are replayed through the app's real `submitScore()` path rather than
written as pre-baked results, so ranks, grades, points and group totals are
computed by the same code the app uses normally.

## Multi-institution setup

The app is built to be sold to several institutions, each with **their own
Firebase project**. Nothing about a project is compiled in: it's resolved
at startup by `mobile/www/js/app-config.js`, in this order.

| Source | Who sets it up | Used by |
|---|---|---|
| `mobile/www/js/build-config.js` | you, at build time | a per-institution APK — nobody sets anything up |
| Config saved on the device | the institution's admin, once per device | the generic APK's setup screen |
| Neither | nobody | Local Test Mode (demo/offline) |

**Why one project each, rather than one shared project:** each institution
stays inside its own no-cost Spark quota, so your hosting cost stays zero
however many you sell; and isolation is physical rather than a rules
predicate, which matters because this data is largely about minors.

A Firebase **web** config is not a secret — it ships in the source of every
Firebase web app, and access is controlled by `firestore.rules` and Firebase
Auth, not by hiding these values. That's what makes it safe to paste into
the app, bake into a build, or email to an admin.

### Building an APK for one institution

Run the **Android build** workflow from the Actions tab with
`institution_name` and `firebase_config` filled in. The build bakes them into
`build-config.js` (via `mobile/scripts/write-build-config.mjs`, which fails
the build on a malformed config rather than shipping an APK that silently
falls back to the setup screen). Leave both blank for the generic APK.

### Onboarding one institution

1. **They create a Firebase project** (better theirs than yours — it keeps
   data ownership and project quotas with them) and add you as a member.
2. **Enable Authentication → Email/Password**, and create Firestore.
3. **Deploy the rules**:
   ```
   firebase deploy --only firestore:rules,firestore:indexes --project <their-project-id>
   ```
4. **Create their admin**: add the user under Authentication, then create a
   Firestore document `roles/{that user's uid}` with `role: "admin"`.
   Judges get `roles/{uid}` = `{ role: "judge", judgeId: "<their judges/ doc id>" }`.
5. **Give them the app** — either their own APK (step above) or the generic
   one plus their config to paste in.

### Why no Cloud Functions

Cloud Functions and Cloud Storage both require Firebase's paid **Blaze**
plan, so this app uses neither and runs entirely on the no-cost Spark plan:

- **Result computation** runs on the client (`mobile/www/js/scoring.js`),
  shared by both backends rather than duplicated server-side.
- **Student photos** are stored inline on the student document as data URLs.
  `resizeImageFile()` caps them at 480px (~10–30KB), well inside Firestore's
  1MB per-document limit.
- **Roles** live in `roles/{uid}` documents that the app cannot write, read
  by `firestore.rules` via `get()`, instead of custom auth claims (which need
  the Admin SDK, i.e. a server).

The trade-off worth knowing: because there's no server, the client that
submits the final score also writes the result. Rules restrict **who** may
write a result and **what shape** it takes, but cannot verify the marks were
averaged honestly. Publishing stays admin-only, so nothing reaches the public
screen without an admin acting. For a fest run by its own staff that's a
reasonable trade; if you ever need it airtight, move `maybeFinalizeItem` back
into a Cloud Function on Blaze.

## Getting Started

1. **Try it with no setup at all** — install the app and tap "Try it without
   a project" for Local Test Mode, then "Load demo data".
2. **For a real fest**, follow *Onboarding one institution* above.
3. **Try it in a browser** (fastest iteration loop — no native build needed):
   ```
   cd mobile/www && npx serve .
   ```
4. **Build the native Android app**:
   ```
   cd mobile
   npm install
   npx cap sync android
   cd android && ./gradlew assembleDebug
   ```
   The APK lands at `mobile/android/app/build/outputs/apk/debug/app-debug.apk`.
   This same sequence runs in `.github/workflows/android-build.yml` on every
   push, so a debug APK is also downloadable from the Actions tab without a
   local Android SDK.

### Seeding an Admin user

Create the user under Firebase console → Authentication, then add a Firestore
document at `roles/{that user's uid}` with the field `role: "admin"`.

`roles` is deliberately unwritable from the app (`firestore.rules` denies all
writes to it), which is what makes it trustworthy as the source of authority —
so this one step is done by hand in the console rather than in the UI. Judges
are seeded the same way, with `{ role: "judge", judgeId: "<their judges/ doc id>" }`.
